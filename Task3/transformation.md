# Трансформация и целевая архитектура

Исходные данные: требования и ограничения – [Task1](../Task1/requirements.md), проблемные зоны и зависимости – [Task2](../Task2/as-is-analysis.md).

## Точки трансформации

### Точка 1. Стабилизация слоя интеграций

| Поле | Содержание |
|---|---|
| Название точки | Стабилизация слоя интеграций |
| Проблема AS-IS | Разная семантика доставки сообщений, защита от дублей ненадёжна, дубли заявок разбирают вручную. |
| Бизнес-влияние | Более предсказуемо обрабатывала заказы. |
| Почему этот участок | Трогать транзакцию оформления на первом этапе рискованно, а интеграции вне оформления с ней мало связаны: их можно стабилизировать, не задевая оформление. |
| Ограничение | Переход на единый способ доставки сообщений потребует доработок: семантика доставки в интеграциях разная. Актуальной схемы потоков данных нет. |
| Зависимости | Точка 4: интеграции переходят на канонический набор событий заказа. |
| Изменение | Унифицируем события, убираем часть обмена через БД, выделяем единый контракт статуса доставки. |
| Что не делаем | Не трогаем выбор маршрута доставки и синхронные вызовы внутри оформления. |
| Метрика проверки | Число дублей заявок, которые вручную разбирает поддержка, снизилось с N до M за одинаковые периоды спроса. |
| Риски | Изменение обмена с .NET-сервисом через таблицу Oracle может сломать какую-то часть системы. Пока новую схему запускают по частям, может временно стать хуже видно, что происходит с заказом. |
| Следующий шаг | После стабилизации интеграций – вынесение логики выбора маршрута доставки. |

### Точка 2. Чтение статусов

| Поле | Содержание |
|---|---|
| Название точки | Чтение статусов |
| Проблема AS-IS | Рассинхрон статусов заказа между системами. |
| Бизнес-влияние | Более предсказуемо обрабатывала заказы: клиент видит понятный статус и не обращается в поддержку. |
| Почему этот участок | Трогать транзакцию оформления на первом этапе рискованно, а чтение статусов с ней мало связано: его можно отделить, не задевая оформление и запись статусов. |
| Ограничение | Переходы статусов решают четыре места: Status Management, сервис заказов, платёжный модуль и batch-процедуры. |
| Зависимости | Точка 4: чтение статусов – часть канонического слоя событий и берёт смены статусов прямо из него. |
| Изменение | В слое событий появляется чтение статусов: клиент и поддержка получают человеческий понятный статус, по которому виден контекст заказа. |
| Что не делаем | Не трогаем переходы статусов: у статусов нет одного владельца, но переходы завязаны на создание заказа, оплату и Oracle – это следующий этап. |
| Метрика проверки | Число обращений «почему статус не меняется или меняется странно» снизилось с N до M за одинаковые периоды спроса. |
| Риски | Рассинхрон сохранится: новое чтение может получать изменения с задержкой или не все. Доверие клиента не восстановится. Если слой упадёт, клиент и поддержка не получат статус, но сразу увидят ошибку, а не неактуальный статус. |
| Следующий шаг | Переходы статусов: дать статусам одного владельца. |

### Точка 3. Промо-сервис покрывает больше сценариев

| Поле | Содержание |
|---|---|
| Название точки | Промо-сервис покрывает больше сценариев |
| Проблема AS-IS | Скидка считается в двух местах, запасной расчёт скидки идёт по урезанным правилам. |
| Бизнес-влияние | Более предсказуемо обрабатывала заказы: меньше риск некорректного подсчёта суммы. |
| Почему этот участок | Трогать `createOrder` и Oracle на первом этапе рискованно, а промо-сервис отдельный: его можно доработать, не задевая их. |
| Ограничение | Часть коэффициентов и ограничений промо лежит в Oracle, а промо-сервис используется не во всех сценариях. |
| Зависимости | Нет. |
| Изменение | Промо-сервис покрывает больше сценариев, чтобы меньше заказов уходило в старый расчёт скидки. |
| Что не делаем | Не трогаем надбавки в `createOrder` и запасной расчёт скидки в Oracle. |
| Метрика проверки | Число заказов, скидку для которых считает старая процедура в Oracle, снизилось с N до M за одинаковые периоды спроса. |
| Риски | Логику промо невозможно объяснить без конкретного кейса, поэтому при переносе сценария в промо-сервис можно упустить правило. Изменения в промо-сервисе могут ухудшить время ответа при оформлении: оформление вызывает его синхронно. |
| Следующий шаг | Запасной расчёт скидки в Oracle. |

### Точка 4. Канонический слой событий и происхождение данных

| Поле | Содержание |
|---|---|
| Название точки | Канонический слой событий и происхождение данных |
| Проблема AS-IS | Нет канонической модели заказа, происхождение данных знают только люди. |
| Бизнес-влияние | Более предсказуемо обрабатывала заказы: поддержка понимает состояние заказа, не обходя несколько систем, а бизнес видит в отчётах одинаковые цифры по заказу. |
| Почему этот участок | Трогать Oracle на первом этапе опасно, а канонический слой только берёт из неё данные: его можно выделить, не меняя базу. |
| Ограничение | Серверы на пределе ресурсов: на распродажах у операционной Oracle уже есть сложности с откликом. Реплика для чтения требует нового сервера и ещё одной Oracle, от которой хотят уйти. Писателей статусов трогать опасно, а batch-процедуры и ночные SQL-скрипты меняют статусы прямо в Oracle, в обход кода приложения. |
| Зависимости | Чтение статусов (точка 2) – часть этого слоя. Точка 1 использует тот же набор событий. |
| Изменение | Выделяем единый набор бизнес-событий заказа и описываем потоки данных: кто какие данные читает и откуда берутся поля. Смены статусов слой получает опросом таблиц Oracle с заданной нами частотой: один управляемый читатель вместо многих разрозненных. |
| Что не делаем | Не убираем тяжёлые выгрузки из операционной Oracle, пока не выяснено, кто какие данные читает. |
| Метрика проверки | Время ответа поддержки по проблемным заказам сократилось с N до M минут. |
| Риски | Если опрашивать Oracle слишком часто, на распродажах проблема с откликом сохранится и даже усугубится. Клиент видит новый статус с задержкой до одного интервала опроса. |
| Следующий шаг | Проверить, что у строк со статусом есть время изменения и его обновляют все, кто меняет статус, включая batch-процедуры и SQL-скрипты. |

## Целевая архитектура первого этапа

| Раздел | Содержание |
|---|---|
| Цель первого этапа | Повысить прозрачность заказа для клиента, поддержки и бизнеса, снизить риск что-то сломать при следующих изменениях и подготовить систему к следующим этапам трансформации. |
| Границы | См. раздел «Где проходят границы». |
| Основной сценарий | Смена статуса заказа доходит до клиента: 1) статус меняется в Oracle; 2) слой событий при очередном опросе таблиц замечает смену, сохраняет последний статус у себя и публикует событие в брокер для аналитики и интеграций; 3) клиент синхронным запросом получает у слоя последний сохранённый статус. |
| Исключения | Слой событий недоступен: клиент и поддержка сразу видят ошибку получения статуса, а не неактуальный статус. Так поддержка быстрее и надёжнее ловит сбой, а клиент не пытается оформить заказ повторно. |
| Компоненты | Новые: слой событий со своей БД, брокером и чтением статусов (точки 4 и 2). Меняются: интеграции (точка 1), промо-сервис (точка 3). Без изменений: остальной монолит и Oracle. |
| Данные и состояния | Слой хранит единый набор бизнес-событий заказа, последний статус каждого заказа в новой статусной модели и описание потоков данных. |
| Интеграции | См. раздел «Где проходят границы». |
| Метрики | Метрики проверки в паспортах точек 1–4. |
| Ограничения | Ограничения в паспортах точек 1–4 и раздел «Что опасно трогать на первом этапе». |

### Что остаётся в монолите

- **Order Processing, Payment Orchestration, Delivery Routing** – опасно трогать на первом этапе.
- **Pricing & Promo Logic** – надбавки в `createOrder` остаются, что меняется в промо – в точке 3.
- **Status Management** – переходы статусов остаются, что меняется в чтении – в точке 2.
- **Checkout / Order API** – не входит ни в зоны риска, ни в точки трансформации первого этапа.
- **Уведомления** – без изменений.

### Что изолируется

- **Oracle.** Остаётся на месте, но интеграции, чтение статусов и аналитика больше не читают её напрямую, а получают данные через слой событий. Исключение – тяжёлые отчёты аналитики: их выгрузки остаются в операционной Oracle, пока не выяснено, кто какие данные читает.

### Что выносится первым

- **Точка 4 – самая первая.** Канонический слой событий выделяется в новую часть, от него зависят точки 1 и 2.
- **Точка 2.** Чтение статусов добавляется в слой событий, когда слой начнёт получать смены статусов.
- **Точка 3.** Часть расчёта скидки переходит из пакета `legacy_promo_pkg` в Oracle в промо-сервис. Монолит при этом не меняется: `createOrder` по-прежнему сначала вызывает промо-сервис.

### Где проходят границы

- **Точка 1.** Обмен с партнёрами через общие таблицы Oracle заменяется полноценной интеграцией с контрактом. События интеграции получают по подписке из слоя событий.
- **Точка 2.** Чтение статусов – часть слоя событий: клиенту и поддержке слой отдаёт статус синхронным запросом.
- **Точка 3.** Граница промо-сервиса уже есть: монолит вызывает его синхронно, она не меняется.
- **Точка 4.** Слой событий отдаёт события через брокер по подписке. Подписчики: аналитика и интеграции. Смены статусов слой получает опросом таблиц Oracle с заданной частотой.

### Почему изменения допустимы по риску

- **Точка 1.** Трогать транзакцию оформления на первом этапе рискованно, а интеграции вне оформления с ней мало связаны: их можно стабилизировать, не задевая оформление.
- **Точка 2.** Трогать транзакцию оформления на первом этапе рискованно, а чтение статусов с ней мало связано: его можно отделить, не задевая оформление и запись статусов.
- **Точка 3.** Трогать `createOrder` и Oracle на первом этапе рискованно, а промо-сервис отдельный: его можно доработать, не задевая их.
- **Точка 4.** Трогать Oracle на первом этапе опасно, а канонический слой только берёт из неё данные: его можно выделить, не меняя базу.

### Что опасно трогать на первом этапе

- **Oracle.** Половина логики лежит в процедурах и пакетах, на базе держатся справочники и обмен с интеграциями. Сразу менять базу опасно: что-то может сломаться.
- **Маршрутизация доставки.** Правила живут в четырёх местах, а в процессе много исключений: крупногабарит, частичная поставка, ручная переадресация. Есть риск недооценить исключения логистики.
- **Создание заказа и оркестрация оплаты.** Здесь живут выгрузка партнёрам до оплаты, неоднозначный статус после сбоя, заказ без платёжной сессии, раздельная запись статуса и оплаты, надбавки в коде. Техлид считает замену оформления слишком рискованной и не трогал бы payment orchestration и core order create.
