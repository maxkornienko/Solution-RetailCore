# План переключения

## Паспорт

| Поле | Значение |
|---|---|
| Что переключаем | Запуск канонического слоя событий: аналитика переходит с чтения Oracle на события из слоя, кроме тяжёлых отчётов. |
| Этап roadmap | Этап 1. Канонический слой событий. |
| Точка трансформации | Точка 4. Канонический слой событий и происхождение данных. |
| Тип переключения | Чтение: аналитика получает данные по заказам из событий слоя вместо Oracle. |
| Среда | Limited production: сначала только заказы клиентов из собственных каналов как основа канонической модели, заказы маркетплейсов – позже, у них есть специальные статусы. |
| Зона воздействия | Бизнес, который читает отчёты аналитики по заказам из собственных каналов. Клиент и поддержка не затронуты. |
| Ответственный за go / no-go | Техлид. |

## Цель переключения

Цель переключения – перевести получение данных для отчётов аналитики по заказам клиентов из собственных каналов с чтения Oracle на события из канонического слоя. После переключения система должна стабильно работать, данные в отчётах должны быть корректными и отражать реальность, а время отклика Oracle на распродаже должно оставаться в пределах +N% от базового замера. Чтение Oracle сохраняется как резерв и источник сверки до завершения периода наблюдения: статусы в БД слоя сверяем со статусами в таблицах Oracle, где статус записывается первым.

### Включаем

- Опрос таблиц Oracle с заданной частотой, сохранение последнего статуса в БД канонической модели, публикация событий в брокер.
- Подписка аналитики на события по заказам клиентов из собственных каналов, оформленным после запуска.

### Не включаем

- Заказы, оформленные до запуска: аналитика по ним читает Oracle, как раньше.
- Заказы маркетплейсов: аналитика по ним пока читает Oracle.
- Тяжёлые отчёты аналитики и BI: читают Oracle, как раньше.
- Чтение статусов клиентом и поддержкой – этап 3.
- Интеграции – этап 2.

### Критерии успешного переключения

| Критерий | Целевое значение | Где проверяем | Кто подтверждает |
|---|---|---|---|
| Последний статус заказа в БД канонической модели совпадает со статусом в таблице Oracle | Расхождение только по времени, в пределах одного интервала опроса | Сверка БД слоя с таблицами Oracle по заказам из собственных каналов, оформленным после запуска | Техлид |
| Время отклика Oracle на распродаже | Не больше +N% от базового замера | Мониторинг Oracle | Техлид |

## Условия запуска

Если хотя бы одно условие не выполнено – переключение не начинаем.

| Условие | Тип | Как проверяем | Порог | Ответственный |
|---|---|---|---|---|
| Пробный опрос не перегружает Oracle | Техническое | Замер времени отклика Oracle при пробном опросе | Не больше +N% от базового замера | Техлид |
| Все, кто меняет статус, обновляют время изменения | Данные | Итог проверки этапа 0 | Проверены все писатели статусов, включая batch-процедуры и SQL-скрипты | Техлид |
| Базовые значения метрик замерены | Наблюдаемость | Итог замеров этапа 0 | Есть базовые значения времени отклика Oracle и времени ответа при оформлении на распродаже | Техлид |
| Запуск вне распродаж и периодов высокой нагрузки | Операционное | Календарь распродаж и прогноз нагрузки | Окно запуска не попадает на распродажу или период высокой нагрузки | Техлид |

## Роли и ответственность

| Роль | До переключения | Во время | После |
|---|---|---|---|
| Техлид | Проверяет условия запуска | Решает go / no-go, решает об откате по R1–R4 | Подтверждает критерии успешного переключения |
| Команда разработки | Готовит слой событий, БД канонической модели, опрос Oracle и брокер | Включает части по шагам 1–3, следит за сигналами наблюдаемости | Исправляет ошибки, разбирает заказы на ручной проверке по R4 |
| Аналитика | Готовит подписку и отчёты на событиях | Подписывается на события на шаге 4, следит за отставанием подписчика | Разбирает отчёты, построенные на событиях, по R3 |
| Бизнес-владелец | Знает об окне запуска | – | Читает отчёты по заказам из собственных каналов, получает сообщение об откате, если он был |

## Состояние данных

| Данные | Источник истины до | Источник истины после | Подготовка | Проверка согласованности | При расхождении |
|---|---|---|---|---|---|
| Статус заказа | Oracle | Oracle, слой хранит копию последнего статуса | Слой работает только с заказами из собственных каналов, оформленными после запуска; заказы до запуска не загружаем | Расхождение статусов в БД слоя с Oracle | Ручная проверка по R4, верным считается статус в Oracle |
| События заказа | – | Слой событий: БД канонической модели и брокер | Брокер пуст до шага 3 | Полнота: число событий против числа смен статусов в Oracle | Откат по R2 |
| Данные для отчётов аналитики | Oracle | События слоя – для новых заказов собственных каналов, Oracle – для остальных | Отчёты по-старому из Oracle продолжают строиться как резерв | Статусы, на которых построен отчёт, сверяем с Oracle | Отчёт сохраняем и разбираем по R3 |

## Наблюдаемость

| Что наблюдаем | Сигнал | Норма | Алерт | Ответственный |
|---|---|---|---|---|
| Нагрузка на Oracle | Время отклика Oracle | Не больше +N% от базового замера | Выше +N% – откат по R1 | Команда разработки |
| Расхождение | Число заказов, у которых статус в БД слоя не совпадает с Oracle дольше одного интервала опроса | 0 | Любой такой заказ – ручная проверка по R4 | Команда разработки |
| Свежесть | Время от смены статуса в Oracle до появления в БД слоя | Не больше одного интервала опроса | Больше интервала – откат по R2 | Команда разработки |
| Полнота | Доля смен статусов в Oracle, которые дошли до слоя и брокера | 100% | Меньше 100% – откат по R2 | Команда разработки |
| Отставание подписчика | Число событий в брокере, которые аналитика ещё не прочитала | Не больше N | Больше N дольше одного интервала опроса – откат по R2 | Аналитика |

## Пошаговый сценарий

| Шаг | Когда | Действие | Ответственный | Проверка результата | При ошибке |
|---|---|---|---|---|---|
| 0 | До окна запуска | Проверить условия запуска и принять решение go / no-go | Техлид | Все условия запуска выполнены | No-go, окно переносится |
| 1 | T0 | Запустить слой событий вместе с БД канонической модели | Команда разработки | Слой и БД работают без ошибок | Остановить слой, разобрать ошибки |
| 2 | После проверки шага 1 | Включить опрос Oracle | Команда разработки | Отклик Oracle в пределах +N%, свежесть не больше одного интервала, расхождения нет | Откат по R1 или ручная проверка по R4 |
| 3 | После проверки шага 2 | Включить брокер | Команда разработки | Полнота 100%: все смены статусов из слоя публикуются в брокер | Откат по R2 |
| 4 | После проверки шага 3 | Подписать аналитику на события | Аналитика | Отставание подписчика не больше N, отчёты по заказам из собственных каналов строятся на событиях | Откат по R2 |
| 5 | После шага 4 | Решить: продолжить наблюдение или откатить | Техлид | Критерии успешного переключения выполнены | Откат по R1–R4 |

## Проверки после переключения

### Технические

| Проверка | Ожидаемое значение | Источник | При нарушении |
|---|---|---|---|
| Время отклика Oracle | Не больше +N% от базового замера | Мониторинг Oracle | Откат по R1 |
| Свежесть | Не больше одного интервала опроса | Мониторинг слоя | Откат по R2 |
| Отставание подписчика | Не больше N | Мониторинг брокера | Откат по R2 |

### Данные

| Проверка | Ожидаемое значение | Как сверяем | При расхождении |
|---|---|---|---|
| Полнота | 100% | Число смен статусов в Oracle по времени изменения против числа событий в брокере | Откат по R2 |
| Расхождение статусов | 0 заказов, расходящихся дольше одного интервала | Сверка БД слоя с таблицами Oracle | Ручная проверка по R4 |
| Дубли событий | 0 | Число повторных событий об одной смене статуса | Откат по R2 |

### Новый контур относительно старого

| Сценарий | Ожидаемое поведение нового контура | Как сравниваем со старым | Допустимое расхождение | При отклонении |
|---|---|---|---|---|
| Смена статуса заказа из собственного канала | Слой замечает смену при очередном опросе и публикует событие | Сверка статуса в БД слоя со статусом в таблице Oracle | Только по времени, в пределах одного интервала опроса | Ручная проверка по R4 |
| Отчёт аналитики по заказам из собственных каналов | Строится на событиях слоя | Статусы, на которых построен отчёт, сверяем с Oracle | Только по заказам, сменившим статус за последний интервал перед границей отчёта | Отчёт сохраняем и разбираем по R3 |

### Операционные

| Проверка | Кто проверяет | Ожидаемое состояние | При проблеме |
|---|---|---|---|
| Отчёты по заказам до запуска и по маркетплейсам строятся из Oracle, как раньше | Аналитика | Без изменений | Откат по R2 |
| Клиент и поддержка не замечают переключения | Техлид | Число обращений из-за непонятного статуса не выросло относительно базового замера | Разобрать причину вместе с поддержкой |

### Стабилизация

| Период | Что должно быть стабильно | Порог | Решение |
|---|---|---|---|
| Первые интервалы опроса | Отклик Oracle, свежесть, полнота | По нормам наблюдаемости | Продолжить или откатить по R1–R2 |
| Первый день | Расхождение статусов, отставание подписчика | По нормам наблюдаемости | Продолжить или откатить по R2, R4 |
| Первая распродажа после запуска | Время отклика Oracle | Не больше +N% от базового замера | Продолжить или откатить по R1 |
| Первая неделя | Все сигналы наблюдаемости | По нормам наблюдаемости | Завершить наблюдение и подключать заказы маркетплейсов или откатить |

## Сценарий отката

### Когда и как откатываем

| ID | Условие | Шаг отката | Кто решает |
|---|---|---|---|
| R1 | Сработало условие остановки: время отклика Oracle выросло больше чем на N% относительно базового замера | Остановить слой событий, чтобы он перестал опрашивать Oracle, и вернуть аналитику на чтение Oracle | Техлид |
| R2 | Аналитика получает события с потерями, дублями или задержкой больше одного интервала опроса | Вернуть аналитику на чтение Oracle – резервный путь | Техлид |
| R3 | Пока контур работал, бизнес видел отчёты, построенные на событиях | Сохранить эти отчёты и вручную разобрать, почему они так сформировались | Техлид |
| R4 | Статус заказа в БД слоя расходится со статусом в Oracle дольше одного интервала опроса | Передать заказ в ручную проверку. Верным считается статус в Oracle | Техлид |

### Состояние после отката

| Область | Ожидаемое состояние | Как проверяем |
|---|---|---|
| Аналитика | Читает Oracle, как до переключения | Отчёты по заказам из собственных каналов строятся из Oracle |
| Oracle | Слой её не опрашивает, отклик вернулся к базовому значению | Мониторинг Oracle |
| БД слоя и события в брокере | Сохранены для разбора ошибок | Данные доступны команде разработки |
| Отчёты на событиях | Сохранены и разобраны по R3 | Итог разбора у аналитики |
| Заказы с расхождением | Переданы в ручную проверку по R4 | Список заказов у команды разработки |
| Бизнес-владелец | Знает об откате и о том, какие отчёты строились на событиях | Сообщение отправлено |
